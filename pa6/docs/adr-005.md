# ADR-005 — Sequential checkout saga with bounded compensation

**Status:** accepted
**Date:** 2026-11-02

## Context

The checkout process coordinates four downstream services: payment, inventory, shipping and notification. These services are independent, and the orchestrator does not control their internal operations. A failure after one or more successful steps can therefore leave the order in a partially completed state.

Writing the OpenAPI contract before implementation forced several decisions to become explicit. The contract defines the `Idempotency-Key` header, request validation, response status codes and error responses. It also limits the number of order items to 100. Because the canonical order schema does not define this limit, the contract and runtime validation must enforce it explicitly.

The most difficult issue was compensation. Payment provides a refund operation and inventory provides a release operation, but shipping and notification have no corresponding compensating endpoints. Therefore, the orchestrator cannot guarantee a complete rollback after those services have performed their actions.

Idempotency introduced another problem: a second request using the same key can arrive while the first checkout is still running. Returning a second execution would risk duplicate payments or reservations. The orchestrator must distinguish an in-progress request from a completed request and a request using the same key with a different payload.

Timeouts also need different treatment from business failures. A downstream service can reject an operation, or it can fail to respond within `REQUEST_TIMEOUT_MS`. Compensation itself can fail, so the final response must report that failure rather than incorrectly claiming that the checkout was fully rolled back.

## Decision

We chose a sequential orchestration-based saga. Each downstream operation starts only after the previous operation succeeds:

1. Authorize payment.
2. Reserve inventory.
3. Create shipping.
4. Send notification.

The orchestrator calculates the order amount using integer cents (`BigInt`) to avoid floating-point rounding errors. The recipient is taken from the customer's email address in the canonical order.

The implementation records each downstream operation in a trace, including its step name, status, start time, finish time and duration. `AsyncLocalStorage` keeps each checkout's trace separate, preventing concurrent requests from mixing their trace entries.

If an operation fails or times out, the orchestrator compensates successful reversible operations in reverse order:

1. Release inventory, if it was reserved.
2. Refund payment, if it was authorized.

Shipping and notification have no compensation operations. Their effects cannot be undone by this implementation.

Axios timeout errors are recorded as timeouts, while downstream business errors are recorded as failures. The orchestrator returns HTTP 504 for timeouts and HTTP 422 for business failures. If a compensation operation fails, it returns HTTP 422 with the error code `compensation_failed`.

Idempotency records are persisted in `/data/idempotency-store.json`. A completed request with the same key and payload replays the stored HTTP status and response body without executing the saga again. A different payload with the same key returns HTTP 409 (`idempotency_payload_mismatch`). A request using a key that is already in progress returns HTTP 409 (`idempotency_conflict`).

Saga results and traces are also persisted in `/data/saga-store.json`, allowing completed results to survive an orchestrator restart.

## Alternatives considered

**Parallel downstream requests:** We considered running independent operations concurrently to reduce checkout time. We rejected this because the checkout requires controlled execution order, and parallel execution would make failure handling and compensation more complicated. Sequential execution makes the saga's state and rollback order predictable.

**Choreography instead of orchestration:** PA5 used event-driven choreography, where services react independently to events. This is useful for loosely coupled asynchronous workflows. However, checkout needs a clear, synchronous result and coordinated reverse-order compensation. Central orchestration provides better control over this process, although it introduces more responsibility into the orchestrator.

**Adding compensation endpoints to shipping and notification:** This would allow more complete rollback. However, the existing downstream services do not provide these operations, and adding them would require changing services outside the orchestrator's control. We therefore accepted the limitation rather than pretending that all steps could be reversed.

**Generating runtime validation from the OpenAPI contract:** This could reduce duplicated schema definitions and the risk of contract drift. We retained the canonical order schema for runtime validation and explicitly represented the API contract in OpenAPI. The trade-off is that constraints such as the 100-item limit must remain consistent in both places.

**Returning an asynchronous pending response:** Another possibility was to return HTTP 202 and let clients check the checkout status later. We rejected this because the assignment requires a synchronous checkout result. The current implementation instead returns the final result or an in-progress conflict for a duplicate key.

## Consequences

The sequential saga makes the checkout process easier to understand, test and trace. Persistent idempotency records prevent completed requests from being executed again after a restart. However, the orchestrator must explicitly manage execution order, timeouts, compensation and stored state.

The most important limitation is that compensation is not a complete rollback. If shipping succeeds and notification subsequently fails, the orchestrator can release inventory and refund payment, but it cannot cancel the shipment. An external shipment may therefore remain active even though the checkout response reports failure.

Adding a fifth downstream step requires updating the execution sequence, timeout and failure handling, trace, and compensation logic if the new step is reversible. The contract and tests must also be updated where necessary.

Idempotency protects requests using the same key, but two concurrent requests with different keys for the same `orderId` are not fully coordinated. Because saga records are keyed by order ID, one execution can overwrite the other's stored saga record.

If `REQUEST_TIMEOUT_MS` is configured too low, a healthy downstream service may be treated as timed out simply because it responds too slowly. The timeout must therefore be chosen with the expected service response time in mind.

Finally, if the orchestrator is terminated during a saga, its persisted idempotency record can remain `in_progress`. A later request with the same key receives HTTP 409 rather than automatically resuming or recovering the interrupted saga. Recovery and stale-operation handling are not implemented in this version.

These limitations are accepted for this assignment. They identify the main areas that would need improvement before using the orchestrator in a production checkout system.
