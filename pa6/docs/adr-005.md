# ADR-005 — Sequential checkout saga with bounded compensation

**Status:** accepted  
**Date:** 2026-11-02

## Context

Checkout coordinates four independent services: payment, inventory, shipping and notification. A failure after an earlier operation succeeds can leave the order partially completed. The orchestrator therefore needs a defined execution order, failure policy and compensation strategy.

The OpenAPI contract was written before implementation. It defines the `Idempotency-Key`, request validation, response codes and a 100-item limit that is not present in the canonical order schema. Runtime validation must enforce the same limit.

Only payment and inventory expose compensating operations (refund and release). Shipping and notification cannot be reversed by this implementation. Duplicate requests also need careful handling: re-running a checkout can cause duplicate charges or reservations. Finally, a downstream business rejection differs from a timeout, and compensation can itself fail.

## Decision

We chose a sequential, orchestration-based saga. The four forward operations run only after the preceding operation succeeds:

1. Authorize payment.
2. Reserve inventory.
3. Create shipping.
4. Send notification.

The orchestrator calculates the total in integer cents using `BigInt`, avoiding floating-point rounding, and sends the customer's email address to notification.

Each downstream call is added to a trace with its step, outcome, timestamps and duration. `AsyncLocalStorage` keeps traces separate across concurrent requests.

On failure or timeout, successful reversible operations are compensated in reverse order: release reserved inventory, then refund authorized payment. Shipping and notification have no compensation endpoint, so their effects may remain.

Axios timeout errors produce HTTP 504 with code `timeout`; business failures produce HTTP 422. If either compensation fails, the result is HTTP 422 with `compensation_failed` and status `failed`.

Idempotency records are stored in `/data/idempotency-store.json`. The same key and payload replay the original HTTP status and response without rerunning the saga. Reusing a key with a different payload returns HTTP 409 (`idempotency_payload_mismatch`); using a key while its request is in progress returns HTTP 409 (`idempotency_conflict`). Saga traces and outcomes are stored in `/data/saga-store.json`.

## Alternatives considered

**Parallel requests:** Rejected because execution order and compensation become harder to control. Sequential calls make the process predictable.

**Event choreography:** PA5 used event-driven choreography. For this synchronous checkout, central orchestration gives a clearer final result and controls reverse-order compensation, at the cost of more responsibility in one service.

**Compensating shipping and notification:** These endpoints do not exist in the supplied services. Adding them would require changes outside the orchestrator, so incomplete rollback is accepted and documented.

**Generating validation from OpenAPI:** This could reduce contract drift. Instead, runtime validation uses the canonical schema and the API contract separately; the 100-item constraint must therefore stay aligned.

**Asynchronous HTTP 202 workflow:** Rejected because this assignment requires a synchronous result. A duplicate in-progress request receives 409 instead.

## Consequences

Sequential execution is easier to trace and test, while persisted idempotency results survive orchestrator restarts. The orchestrator must manage ordering, timeouts, compensation and storage itself.

Compensation is not a full rollback: if shipping succeeds and notification fails, inventory can be released and payment refunded, but the shipment cannot be cancelled. Adding a downstream step also requires updating execution, failure handling, tracing, tests and any applicable compensation.

Different idempotency keys for the same `orderId` are not coordinated; because saga records are keyed by order ID, one can overwrite another. A low `REQUEST_TIMEOUT_MS` can classify a slow but healthy service as timed out.

If the process stops during a saga, its persisted record may remain `in_progress`; a retry then receives 409. Automatic recovery and stale-operation handling are not implemented. These limitations are accepted for this assignment and would need attention before production use.
