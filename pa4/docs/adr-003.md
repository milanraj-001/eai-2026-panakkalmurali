# ADR-003 — Translator/enricher/filter pipeline with per-item enrichment failure isolation

**Status:** accepted
**Date:** 2026-10-11

## Context

The B2B fixture declares `encoding="windows-1257"` in its XML prolog.
Reading it as UTF-8 instead of raw bytes silently corrupts `Bērziņa` and
`Brīvības iela` into garbage with no thrown error — the same failure mode
as PA1's fixed-width file, applied to XML.

The three sources' product id formats are incompatible: web's `PROD-001`
is already correct, mobile's bare `001` needs a prefix, B2B's
`SKU-PROD-001` needs a prefix stripped. Getting any one wrong sends a
well-formed but wrong id to the pricing API, which returns a 404 rather
than an obviously broken error.

The pricing API's `4.5` unit price (`PROD-013`) is the concrete case
`toDecimalAmount` exists for: `String(4.5)` gives `"4.5"`, not `"4.50"`,
and the public amounts test checks for exactly two fraction digits.

Each source hides payment details differently: web nests it under
`customer.payment`, mobile flattens it into top-level `pm`/`pan`/`pexp`,
B2B buries it inside `BuyerParty`. None of the three `CanonicalOrder`
mapping code paths reference these fields at all.

## Decision

`normalizeProductId(source, rawId)` applies one transformation per source:
web passes the id through, mobile prepends `"PROD-"`, B2B strips a leading
`"SKU-"` with a regex. `toDecimalAmount(price: number)` is
`price.toFixed(2)` — the API already returns a number, so this function
only formats, it does not do arithmetic.

`enrichFromPricing` returns a discriminated union: `"ok"` with the
formatted price, `"unknown_product"` on a 404, `"error"` with the HTTP
status (or `0` on a network failure) on anything else, including a 500.
`enrichItems` calls this per line item and never lets one bad line stop
the others: a failed line becomes a `TransformWarning`, not a dropped
order. If every item fails, the function returns `order: null` rather
than an order with zero items, since the schema requires `minItems: 1`.

Payment data is filtered by omission: each translator's `customer` object
literal only ever reads `name`, `email`, `address` off the parsed source.
The raw payment fields still exist in memory as parsed objects — they are
simply never referenced when building the return value.

## Alternatives considered

I considered representing `unitPrice` as integer cents instead of a
decimal string, to sidestep string formatting entirely. I rejected this
because the canonical schema itself fixes the decimal-string format —
switching to cents would just move the conversion problem to whoever
reads `unitPrice` next, at the cost of an extra translation layer I don't
own either.

I considered failing an entire order the moment any single line item
could not be priced, instead of dropping just that item. I rejected this
because it turns one bad product id in a 10-item order into zero
recoverable information about the other 9 items — worse for any
downstream consumer than 9 priced items plus one named warning.

## Consequences

If the canonical schema gains a required field next semester, all three
`translateX` functions need updating independently — there is no shared
mapping layer a schema change could be applied to once.

If a fourth source arrives with an unrecognized product id format, calling
`normalizeProductId` with a fourth source literal is a TypeScript compile
error (`"web" | "mobile" | "b2b"`), forcing a conscious decision rather
than silently falling through at runtime.

`enrichItems` calls the pricing API once per line item, sequentially, with
no caching — an order with repeated products makes one HTTP round trip per
line, not per distinct product. I accepted this latency and load cost in
exchange for not needing a cache-invalidation strategy, since the mock
catalog's admin endpoint exists specifically to test that a live price
change is reflected immediately, which a naive cache risks missing.
