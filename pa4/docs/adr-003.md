# ADR-003 — Translator/enricher/filter pipeline with per-item enrichment failure isolation

**Status:** accepted
**Date:** 2026-10-11

## Context

The B2B fixture declares `encoding="windows-1257"` in its XML prolog. Reading
`b2b-order.xml` with `readFileSync(path, "utf8")` instead of raw bytes would
have silently corrupted `Bērziņa` and `Brīvības iela` into garbage with no
thrown error — the exact same failure mode as PA1's fixed-width file, applied
to XML this time.

`fast-xml-parser`'s behavior for `<LineItem>` mattered concretely:
`LineItems.LineItem` comes back as a single object when there is exactly one
line item, and an array when there is more than one. Both fixtures in this
assignment have two line items, so `Array.isArray(rawLineItems) ? rawLineItems
: [rawLineItems]` never actually branches into the single-object case during
testing — but the type comment in the starter explicitly warns this is not
guaranteed to stay true, so the normalization is there regardless of whether
the current fixtures exercise it.

The three sources' product id formats are genuinely incompatible with each
other: web's `PROD-001` is already correct, mobile's bare `001` needs a
prefix, and B2B's `SKU-PROD-001` needs a prefix stripped. Getting any one of
these three normalization rules wrong silently sends a correctly-formatted
but wrong id to the pricing API, which would return a 404 rather than an
obviously-broken error.

The pricing API's `4.5` unit price (`PROD-013`) was the concrete case that
made `toDecimalAmount` matter: `String(4.5)` gives `"4.5"`, not `"4.50"`, and
the public amounts test checks for exactly two fraction digits across all
three sources.

Each source hides its payment details differently: web nests it under
`customer.payment`, mobile flattens it into top-level `pm`/`pan`/`pexp`
fields, and B2B puts it somewhere inside `BuyerParty` alongside the fields I
do map. None of the three TypeScript interfaces for these raw shapes include
a `payment` field in the `CanonicalOrder` type at all — the filter is
enforced structurally, by what the mapping code reads and copies forward,
not by an explicit "remove payment" step.

## Decision

`normalizeProductId(source, rawId)` applies one of three string
transformations keyed on the source literal: web passes the id through
unchanged, mobile prepends `"PROD-"`, and B2B strips a leading `"SKU-"` with
`rawId.replace(/^SKU-/, "")`.

`toDecimalAmount(price: number)` is exactly `price.toFixed(2)` — the pricing
API already returns a number, so this function's only job is formatting, not
arithmetic, per the TODO's instruction not to round-trip through a float
representation more than once.

`enrichFromPricing` distinguishes three outcomes via a discriminated union
(`EnrichResult`): `"ok"` with the formatted price, `"unknown_product"` on a
404, and `"error"` with the HTTP status (or `0` for a network failure) on
anything else, including a 500. `enrichItems` calls this once per line item
and never lets one bad line stop the others: an `"unknown_product"` or
`"error"` result becomes a `TransformWarning` pushed to the warnings array,
while the successful lines still become `CanonicalItem`s. A `TransformResult`
whose `items` array ends up empty (every line item failed) returns
`order: null` rather than a `CanonicalOrder` with zero items, since the
canonical schema requires `minItems: 1`.

Payment data is filtered by omission, not by deletion: each translator's
object-literal construction of `CanonicalOrder.customer` only ever reads
`name`, `email`, and `address` off the parsed source object. `WebOrderInput`,
`MobileOrderInput`, and `ParsedB2BOrder` all still *contain* the payment
fields as parsed TypeScript objects in memory — they are simply never
referenced when building the return value, so there is no field to
accidentally leak by typo later.

## Alternatives considered

I considered representing `unitPrice` as an integer number of cents (e.g.
`2250` instead of `"22.50"`) to avoid decimal-string formatting entirely. I
rejected this because the canonical schema itself fixes `unitPrice` as a
decimal string — converting to cents would require a second conversion step
at every point this value is read elsewhere in a larger system, and it does
not sidestep the original problem so much as move it to whoever reads
`unitPrice` next.

I considered failing an order entirely (returning `order: null`) the moment
any single line item could not be priced, rather than dropping just that
item and continuing. I rejected this because it would turn one bad product
id in a 10-item order into zero recoverable information about the other 9
items, which is strictly worse for whoever consumes this pipeline than a
9-item order plus one clearly-flagged warning — the same "one bad record
should not take down the whole batch" reasoning as PA1's malformed line.

## Consequences

If the canonical schema gains a required field next semester that none of
the three source formats naturally provide (e.g. a `shippingMethod`), every
one of the three translator functions needs an explicit update to supply it
— there is no shared mapping layer between the three `translateX` functions
that a schema change could be applied to once; each one independently
constructs its own `CanonicalOrder` object literal.

If a fourth source arrives with a product id format `normalizeProductId`
has never seen, calling it with a fourth source literal is a TypeScript
compile error (the parameter type is `"web" | "mobile" | "b2b"`), which is a
deliberate cost: it forces a conscious decision about the new format's
normalization rule rather than silently falling through an unhandled case
at runtime.

The enrichment loop in `enrichItems` calls `enrichFromPricing` once per line
item, sequentially, with no caching — an order with many line items of the
same product makes one HTTP round trip per line rather than one per distinct
product id. At real traffic volumes this is a real latency and pricing-API
load cost I accepted in exchange for the simplicity of not needing a cache
invalidation strategy for prices that can themselves change at runtime (the
mock catalog's admin endpoint exists specifically to test that a price
change is reflected immediately, which a naive per-order cache would risk
missing).
