# ADR-002 — Idle-timeout aggregation keyed by orderId and itemIndex

**Status:** accepted
**Date:** 2026-10-03

## Context

Correlation had to survive the splitter turning one order into N
independent messages travelling three different queues at different
speeds. The constraint: `orders.physical`, `orders.digital`, and
`orders.subscription` have no shared ordering guarantee between them, so
the aggregator has no way to know "this is item 2 of order X" unless every
message explicitly carries that information itself.

The timeout mechanism was fixed by the assignment (an idle timeout, reset
on each result received, read from `AGGREGATOR_IDLE_TIMEOUT_SECONDS`), but
the production value was genuinely open. During testing, `router-service`
and `aggregator-service` both crashed once on first startup with
`pika.exceptions.AMQPConnectionError`, because RabbitMQ's healthcheck
(`rabbitmq-diagnostics -q ping`) reported healthy slightly before the
broker was actually ready to accept AMQP connections. That crash is
unrelated to my aggregation code, but it sharpened what "too short" a
timeout actually costs: an idle timeout needs enough margin that transient
infrastructure hiccups (a slow worker restart, a brief network blip) don't
masquerade as a dead worker.

What a "partial" result needed to contain was not fully obvious from the
message shape alone until I worked through who would consume
`orders.complete` downstream — a caller cannot act on "this order didn't
finish" without knowing exactly which item(s) to retry.

Duplicate handling was a real decision, not a formality: RabbitMQ
redelivers a message whenever a consumer acks late or a connection drops
mid-processing, so a duplicate `itemIndex` arriving on `orders.results` is
an expected, not exceptional, event.

## Decision

Every item message `router_service.route_order` publishes carries the
same `orderId`, `correlationId` (identical to `orderId`), and `totalItems`
(the original order's item count) regardless of which queue it is routed
to. These three fields never vary across an order's split messages — only
`itemIndex` and `item` differ per message.

`aggregator_service.in_flight` is a dict keyed by `orderId`, and within
each order's entry, results are stored in a nested dict keyed by
`itemIndex`: `entry['items'][item_index] = result`. A redelivered result
for the same `itemIndex` overwrites the existing entry rather than adding
a new one, so `len(entry['items'])` is always a count of distinct items,
never of messages received. `aggregate_result` and `sweep_timeouts` both
hold `lock` only while mutating `in_flight`, and call
`publish_completion()` only after releasing it, so two orders being
processed concurrently (or a sweep running mid-processing) cannot corrupt
each other's state.

`entry['last_activity']` is reset to `time.time()` on every call to
`aggregate_result` for that order, and `sweep_timeouts` runs every
`SWEEP_INTERVAL_SECONDS` (1 second) checking
`now - entry['last_activity'] > IDLE_TIMEOUT_SECONDS`. This is an idle
timeout, not a deadline from order creation — a 50-item order whose
workers are all still slowly answering has its clock reset on every
arrival and never times out mid-flight, as long as no single gap between
results exceeds the threshold.

A partial completion message sets `status: "partial"` and computes
`missingItemIndexes` as every index in `range(total_items)` not present
in `entry['items'].keys()` — so the caller receiving `orders.complete`
knows exactly which items to retry, not just that something is missing.

## Alternatives considered

I considered a fixed deadline measured from when the order first arrived,
rather than an idle timeout reset per result. I rejected this because it
directly conflicts with handling large orders correctly: a 50-item order
whose workers are each individually healthy but collectively slow would
still be actively making progress at, say, the 6-second mark under a
fixed 5-second deadline, and would be incorrectly flagged partial even
though nothing has actually failed. An idle timeout only fires when
progress has genuinely stalled, which is the actual failure condition the
assignment cares about.

I considered deduplicating by configuring the queue consumer with
auto-ack instead of tracking `itemIndex` myself, on the reasoning that a
message acked immediately on receipt can't be redelivered at all. I
rejected this because it reintroduces exactly the failure mode manual ack
exists to prevent (from PA2): if the aggregator process crashes between
receiving a message and recording it in `in_flight`, an auto-acked message
is gone forever with no redelivery, silently undercounting that order
rather than safely retrying.

## Consequences

`in_flight` is a plain Python dict in the aggregator process's memory. If
the aggregator container restarts mid-order, every order that was
partially collected is lost entirely — not flagged partial, simply gone,
since there is no persistence layer backing it. At ten times the current
traffic, this also means the aggregator cannot run as more than one
replica: two aggregator processes would each hold a different, incomplete
view of `in_flight` for the same order, and whichever one happened to
receive the Nth result would be the only one able to detect completion.

For production, I'd run `AGGREGATOR_IDLE_TIMEOUT_SECONDS` meaningfully
higher than the 5-second test value — on the order of 30-60 seconds — set
by measuring actual p99 worker processing latency rather than guessing,
since the test value of 5 seconds is tuned for fast test execution, not
for distinguishing "worker is slow" from "worker is dead" under real
production latency variance.

The in-memory approach is also why a worker crash during the startup
race I observed (`pika.exceptions.AMQPConnectionError` on `router-service`
and `aggregator-service` at first boot) would have silently dropped any
order already in flight at that moment — the compose file has no
`restart` policy on these services, so a crashed container stays crashed
until something manually restarts it, with no retry loop of its own
unlike PA2's producer/consumer.
