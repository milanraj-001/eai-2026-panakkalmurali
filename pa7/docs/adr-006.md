# ADR-006 — Checkout saga as a Temporal workflow, with failure classification in the activities

**Status:** accepted
**Date:** 2026-11-09

## Context

My PA6 orchestrator keeps a saga's progress in memory. The trace lives in an `AsyncLocalStorage` (`traceStorage`, `server.ts:73`), and only `finishCheckout` (`:457`) writes the saga store. `POST /checkout` first writes an idempotency record in state `in_progress` with an empty trace (`:283-292`). If I `docker kill pa6-orchestrator` while shipping is slow, payment and inventory have already happened, but nothing on disk says so. The record stays `in_progress`, every retry with that key gets `409 idempotency_conflict`, and nothing refunds the payment. ADR-005 accepted this limit; PA7 removes it.

Porting raised two more problems. `callStep` treats every non-timeout failure alike (`service_error`), but Temporal needs to know which failures may be retried: a declined payment must not be tried three times. And the workflow sandbox refuses what PA6 used freely: `axios`, `process.env`, `AsyncLocalStorage`.

## Decision

One activity per HTTP call, six in all (`activities/index.ts`), and a workflow that holds only the saga logic (`workflows/checkout.ts`) and does no I/O.

An activity decides if a failure is permanent. A 4xx throws `ApplicationFailure.nonRetryable` with the mock's `code` as its type. A 5xx, or no answer, throws a retryable failure. A slow call throws nothing: `startToCloseTimeout` fails the attempt, and the workflow maps the `TimeoutFailure` to code `timeout`.

The retry policy is 3 attempts, 200 ms initial interval, coefficient 2, with the given 2.5 s timeout. A call that keeps timing out fails its step after about 8 s: long enough to ride out a short outage, short enough that the api still answers.

Compensation is plain code: `compensate` calls `releaseInventory`, then `refundPayment`, and the workflow returns a `CheckoutResult` for every outcome. As in PA6, a failed release does not stop the refund attempt. `calculateAmount` stays in `BigInt` cents.

## Alternatives considered

**Keep the PA6 orchestrator and add a startup recovery job.** This is the real option. The orchestrator would have to write the saga store after every step, and the job would resume from the last recorded step. A crash between "call made" and "step recorded" would still repeat a call, and my payment mock has no idempotency key to absorb it. I would be writing a small workflow engine.

**Retry every failure.** A declined payment would be tried three times, and compensation would start later.

**One activity for the whole saga.** The workflow loses its per-step history, and the Temporal UI shows one opaque box.

## Consequences

Kill the worker mid-saga and the workflow finishes after restart. The Temporal UI shows every attempt, which PA6 never gave me.

Activities run at least once. If the worker dies after a mock has done its work but before Temporal records the result, the call is repeated: shipping would run twice. Had that step been `authorizePayment`, the customer would be charged twice, because my payment mock does not deduplicate. The fix is an idempotency key derived from the order id.

Changing workflow code while workflows run can break replay, so deploys now need versioning discipline. I also operate a Temporal server, its database and a worker, which PA6 did not need. The api's two JSON files are only an audit mirror and can drift from Temporal's history.

## What the engine took over

- **Timeouts.** PA6 gave every axios call `timeout: requestTimeoutMs` and turned `ECONNABORTED` into `"timeout"` by hand (`callStep`, `:162`, `:184`). Now `startToCloseTimeout` does it.
- **Remembering where a saga was.** PA6 kept the trace in `traceStorage` and wrote the saga store only at the end. Now the workflow's history records each step, and replay rebuilds the state after a crash.
- **Idempotency bookkeeping.** PA6 hashed the body, kept the `in_progress` record and answered 409 by hand (`:252-292`). Now the api uses the `Idempotency-Key` as `workflowId`, and Temporal refuses a second workflow with the same id.
- **Atomic state writes.** PA6's `writeStore` wrote a temporary file and renamed it. Temporal persists the history instead.
- **Retry and backoff.** PA6 made one attempt per call, so a 5xx ended the saga. The retry policy now absorbs a short outage with no retry code of mine.
