# ADR-009 — The trace is a wire tap with fire-and-forget hops

Status: accepted

## Context
An operator must see the whole journey of one order across four services. Tracing must never be able to break an order.

## Decision
A wire tap. Every service publishes one hop record per unit of work to the fanout exchange `trace.events`, which feeds the durable queue `trace.store`. The observer consumes that queue and appends each hop to its own store, and serves `GET /trace/:cid`. I chose the wire tap over scatter-gather (which would make the trace request depend on every service being up) and over OpenTelemetry (a heavier dependency, and auto-instrumentation is not allowed).

Publishing a hop is fire-and-forget: a plain publish inside a try, with no broker confirm and no waiting. A failure is swallowed, so the business operation is never blocked or failed by tracing (R-4.8.2). The cost of a lost hop is a gap in the trace, not a lost order.

Causation across a retry: a nack cannot rewrite headers, so every delivery attempt of one message carries the same causationId, the hop that published it. The attempts are told apart by the attempt number from `x-death`, and each failed attempt is followed by a retry hop caused by that attempt's consume hop.

If the observer is down, nothing is lost: hops wait in the durable `trace.store` queue and the observer writes them when it returns. The alert `trace.store` depth is visible in `/ops/metrics`.

## Alternatives considered
- Confirmed hop publishing: stronger, but it adds latency and a failure path to every operation.
- Scatter-gather at query time: fresh, but fragile and slow when a service is down.
- OpenTelemetry: standard tooling, but forbidden as a replacement for my own header propagation.

## Consequences
The trace is eventually complete, not guaranteed complete. A broker outage at the wrong moment can drop hops. I accept that because the trace is for operators, not for the business flow.
