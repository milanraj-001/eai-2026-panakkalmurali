# ADR-007 — The saga is started by an event, not by HTTP

Status: accepted

## Context
In PA6 the saga was started by an HTTP call and answered in the same request. In the capstone, intake only normalizes and accepts an order. The saga runs later, in another service, and a client must never wait for four provider calls. The orchestrator can also crash at any moment, so the work must survive that.

## Decision
Intake publishes the canonical `order.accepted` event to `orders.exchange` with publisher confirms and answers 202 only after the broker has confirmed it. The orchestrator consumes `saga.queue` and runs the saga. For each message it persists the saga state together with its outcome event, then publishes the outcome, and only then acks. Prefetch is at least `SAGA_CONCURRENCY` (5), so five sagas can be in flight; a larger prefetch would only park unacked messages inside the consumer. Steps inside one saga never overlap.

If the orchestrator crashes after persisting the terminal state but before publishing the outcome, the message was never acked, so the broker redelivers it. The orchestrator finds a saga that already has an outcome and republishes the stored envelope with a new messageId, and no step runs again. I checked this by republishing an accepted event: a second `order.completed` appeared and payment still showed one charge.

`GET /orders/:cid` learns the state from `intake.outcomes.queue`, bound to `orders.outcome`. Intake applies only the transitions in an allowed-transitions table, so a late or duplicated lifecycle event is ignored and a terminal state can never move backwards.

## Alternatives considered
- Start the saga by HTTP from intake: simple, but intake would hold the connection open and lose the saga if it died. Rejected.
- Ack before publishing the outcome: faster, but a crash in between loses the outcome event for good. That would need a real outbox. I chose publish-then-ack and accepted duplicate outcome events instead.
- Intake asks the orchestrator for the state on each GET: couples intake to the orchestrator being up. Rejected in favour of the queue.

## Consequences
Outcome events are at-least-once, so every consumer must tolerate duplicates (intake's transition table and the notifier's processed-ids store do). The price of publish-then-ack is that duplicates exist at all. Order state can lag the saga by a moment because it travels through a queue.
