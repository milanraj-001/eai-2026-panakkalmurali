# ADR-008 — Three dedup layers, and at-least-once notices

Status: accepted

## Context
The same order can arrive twice for different reasons, and a provider call can be repeated after a timeout. Each cause needs its own protection, because a failure that one layer misses must be caught by another.

## Decision
Three layers, each catching a failure the others cannot:
- Intake Idempotency-Key (hash of the raw body): catches a client that retries a POST after a network timeout. Same key and same bytes return the same correlationId and publish nothing; a different body under the same key is a 409.
- Saga business key (`source:orderId`): catches the same order submitted again under a new Idempotency-Key. The second order is recorded as `duplicate` and no step runs. This is the scenario "duplicate submission with a new Idempotency-Key".
- Provider keys (`authorize:<businessKey>` and so on): catch the orchestrator repeating a call after an unknown outcome. When payment charged but my call failed, the retry sends the same key and the provider returns the stored answer. I verified one charge after two 503s and after a replay.

Notices are at-least-once, by design. A charge must be exactly-once in effect because repeating it takes a customer's money twice. A duplicate "your order could not be completed" notice is an annoyance, and the notification provider offers no idempotency key, so exactly-once is not available there. The notifier dedupes on correlationId in a persisted store to keep duplicates rare.

Business-key dedupe means a customer whose order was declined cannot retry with the same orderId: that attempt is a duplicate. They must submit a new orderId, which gives a new business key.

## Alternatives considered
- Only the intake key: misses a resubmission with a new key.
- Only the business key: misses a retry that never reached the saga, and does nothing for provider calls.
- Exactly-once notices through a two-phase send: no provider support, so it would be fiction.

## Consequences
A rare second notice is accepted. The business key is a deliberate rule that blocks reuse of an orderId, which the customer-facing side must explain.
