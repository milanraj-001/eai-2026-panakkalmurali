# ADR-010 — Stuck sagas are detected on redelivery and compensated by an operator

Status: accepted

## Context
If the orchestrator dies mid-saga, the provider may already have charged, reserved or shipped. Re-running steps automatically could repeat an effect, and some effects, like a shipment, cannot be undone.

## Decision
Detection rule. Each orchestrator run draws a new run id and stores it with the saga as its owner. A saga message that was not acked comes back after a restart. If that saga already has recorded steps and no outcome, the orchestrator marks it `needs_attention`, writes a `saga.stuck` hop and publishes `order.needs_attention`. Redelivery happens as soon as the consumer reconnects, so this is well inside `SAGA_STUCK_AFTER_MS`. No step is ever re-run automatically.

False positives: a redelivery with steps recorded but still inside a live run, for example after a broker reconnect while a saga is mid-flight, can be marked stuck although nothing crashed. False negatives: a saga whose message was lost cannot be detected by this rule.

Why not resume automatically: the unknown state. A call that timed out may or may not have had its effect, and shipping has no idempotency key. A person decides.

Compensation matrix: standard and express orders compensate in reverse (release inventory, then refund payment); b2b has no payment, so only the release. Shipping and notification have no compensation. `POST /sagas/:cid/compensate` runs only the outstanding compensations, is idempotent, and ends `compensated` with code `operator_compensated`, or `compensation_failed` if a call fails. I verified one refund and one release, and the same answer on a second call.

What an operator must know before pressing compensate: it refunds and releases, but a shipment that already left stays shipped, because the carrier finished the call it was given. Check shipping first.

What Temporal changes: durable execution resumes the workflow itself, so there is nothing stuck to detect. In that mode the stuck list is always empty and compensate answers 409 `saga_not_stuck`.

## Alternatives considered
- Resume from the last step automatically: risks repeating an effect.
- A timer that scans for old sagas: catches more cases, but needs a threshold that cannot tell slow from dead.
- Always compensate automatically: would refund a customer whose shipment is already on the way.

## Consequences
An operator is in the loop for every crash mid-saga. The rule is simple and cheap, but it has the false positives above, and the runbook says how to check before compensating.
