# ADR-000 — Fixed-width, dual-encoding order ingestion with reject-and-continue

**Status:** accepted
**Date:** 2026-09-09

## Context

The order export (data/orders-20260901.txt) is fixed-width and encoded in
CP1257, while the customer master (data/customers.csv) is semicolon-separated
and encoded in UTF-8 — two encodings in one integration, with no indication of
either in the filename or file extension.

Reading the order file with readFileSync(path, "utf8") decodes Latvian
diacritics incorrectly (Bērziņš becomes garbage) without throwing any error —
the program runs cleanly and produces a plausible-looking report that is
silently wrong in every name field.

Line 6 of the order file (ORD-0006  C0000006  Ilze V) is truncated to 26
characters instead of the required 77. Naively splitting each line into
fields by fixed offsets without first checking length either throws (killing
the whole run) or silently reads garbage/empty values into later fields.

The amount field uses a comma as its decimal separator (e.g. 45,20). Routing
this through parseFloat after a naive replace, or converting to a JavaScript
number at any point, drops trailing zeros (45,20 -> 45.2) and can accumulate
floating-point rounding error — both are silent corruption of a monetary
value. Order ORD-0004 also carries a negative amount (-250,00), a legitimate
refund that a naive "amount must be positive" filter would silently discard.

## Decision

ingest() reads the order file as raw bytes via readFileSync (no encoding
argument) and passes them to decodeOrderFile(), which uses
`new TextDecoder("windows-1257")` to decode correctly — no external
dependency required, since TextDecoder is part of the Node/Web platform
standard library.

Each line is checked against ORDER_LINE_LENGTH (77) before any field is
sliced. Lines that don't match are pushed into `rejected` with their 1-based
line number and a reason string, and the loop continues to the next line —
nothing throws, and nothing is silently dropped.

Fields are sliced by fixed column position (ORDER_LAYOUT), not
split on whitespace, so names containing spaces are read correctly.

toIsoDate() rearranges the DD.MM.YYYY string into YYYY-MM-DD using string
splitting only — no `Date` object is constructed, so there's no ambiguous
parsing and no timezone is introduced into a value that doesn't have one.

toDecimalString() replaces the comma with a period as a string operation and
returns a string. `amount` is typed as `string`, never `number`, throughout
the Order interface — this is deliberate, and is what lets 45,20 survive as
"45.20" instead of becoming 45.2.

unmatchedCustomers is computed by parsing the CSV separately, building a set
of customer IDs seen in accepted orders, and reporting any customer ID from
the CSV not in that set.

## Alternatives considered

I considered adding iconv-lite for the CP1257 decoding, since it's the
library most tutorials reach for. I rejected it because Node's built-in
TextDecoder already supports the "windows-1257" label natively, and the
assignment's dependency check (and the point of the exercise) is to notice
that the standard library already solves this — pulling in a package here
would hide the actual lesson about encodings rather than teach it.

I also considered storing `amount` as a `number` and formatting it back to a
string only when writing the JSON report. I rejected this because any
intermediate arithmetic or JSON.stringify on a float risks losing exactly the
trailing-zero information the assignment is testing for (45.20 vs 45.2) —
keeping it a string end-to-end removes that entire class of bug rather than
requiring careful formatting discipline everywhere the value is touched.

## Consequences

This makes the pipeline resilient to malformed individual records — one bad
line doesn't take down the whole ingestion run, and every skipped record is
visible in the output rather than silently vanishing.

It does not handle a change in field order or field width in the upstream
file — if the exporting system inserts a new field in the middle of the
record, ORDER_LAYOUT's column offsets become wrong, and every field after
the insertion point silently reads the wrong bytes without any error, since
line length alone can't detect a shifted layout. A customerName that exceeds
32 characters would silently get truncated at the column boundary rather than
rejected as malformed, since only overall line length is checked, not
per-field content. If the order file arrives as UTF-8 instead of CP1257 by
accident, decodeOrderFile will silently decode it incorrectly, producing
garbled names without throwing — the position-based length check catches
truncation, but not a wrong-but-plausible encoding.

For a system I had to run for five years, I would want either a versioned
layout definition validated against a small self-describing header row, or
(preferably) to push for the upstream system to export JSON or CSV with a
header, since a fixed-width format with no self-description has no way to
detect a layout change until it's already silently corrupting data.
