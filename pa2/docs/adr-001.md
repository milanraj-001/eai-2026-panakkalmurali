# ADR-001 — Durable queue with publisher confirms, manual ack, and property-based correlation

**Status:** accepted
**Date:** 2026-09-20

## Context

Four decisions were forced by the demonstrations, and each one has an
alternative that looks correct right up until the broker is actually
killed.

Publisher confirms is the one that bit hardest. Publishing a batch of
messages with the header `X-Publish-Mode: fire-and-forget` and then running
`docker restart pa2-rabbitmq` made some of those messages vanish entirely,
even though the HTTP client had already received a `202` for every one of
them (04-publisher-confirms-prevents-loss.test.ts). The naive version —
call `channel.publish()`, respond `202` immediately — passed every other
test in the suite; only this restart-based demonstration exposes that the
`202` was a lie about durability.

Durable queue declaration is the cheapest decision and the easiest to skip
by accident, because `channel.assertQueue(name, { durable: true })` behaves
identically to a non-durable declaration right up until
`docker restart pa2-rabbitmq` — at that point a non-durable queue is simply
gone, not just empty (02-broker-restart-survives.test.ts checks the queue
itself survives, before the consumer is even restarted).

Manual ack placement matters at the granularity of a single line of code.
`handleMessage` appends to `data/received.jsonl` before calling
`channel.ack(msg)`. If the process crashed between those two lines with the
order reversed (ack first, write second), RabbitMQ would consider the
message delivered and never redeliver it, even though it was never actually
written to disk.

correlationId propagation is not satisfied by the value merely appearing
somewhere in a log line. It has to travel through a specific chain of
hops — HTTP header (`X-Correlation-Id`, generated with `randomUUID()` if
absent) into the AMQP message's `correlationId` **property** (set in
`publishMessage`'s `publishOptions`, not embedded in the JSON body) and
back out via `msg.properties.correlationId` in `handleMessage` — for the
same ID to genuinely trace one request end to end.

## Decision

`connectProducerChannel` opens a `ConfirmChannel` (not a plain `Channel`)
and calls `channel.assertQueue(queueName, { durable: true })`. Using a
confirm channel is a prerequisite for the next decision — a plain channel
has no confirm callback to publish against.

`publishMessage` sets `persistent: true` in the publish options only when
`mode === "confirmed"`, and in that mode does not resolve its returned
promise until the broker invokes the confirm callback with no error. In
`"fire-and-forget"` mode it calls `channel.publish()` and returns
immediately, with no persistence flag and no confirm wait — this branch
exists solely to make demonstration (c) possible.

`connectConsumerChannel` declares the same durable queue on a plain
`Channel` and calls `channel.prefetch(1)`, so RabbitMQ delivers one
unacknowledged message at a time rather than flooding the consumer.

`handleMessage` reads `msg.properties.correlationId`, parses the message
body, appends a JSON line containing the correlationId, the parsed payload,
and a `receivedAt` ISO-8601 timestamp to `received.jsonl` via
`appendFileSync`, and only then calls `channel.ack(msg)`.

## Alternatives considered

I considered using `channel.publish()`'s boolean return value (whether the
internal write buffer is full) as the sole signal of successful delivery,
skipping the confirm channel and callback entirely. This is close to
correct-looking amqplib code — it does provide a form of backpressure — but
it only tells you whether the message left the producer process's memory,
not whether the broker durably has it. I rejected it because it is exactly
the gap demonstration (c) is built to expose: the return value is `true`
right before a message that a broker restart erases.

I considered acking a message immediately upon receipt, before writing to
`received.jsonl`, on the reasoning that manual ack primarily exists to
support the "stopped consumer" scenario (demonstration b) and doesn't need
to also guard the write. I rejected this because a crash between the ack
and the write is silent data loss with no recovery path — the broker has
already discarded its copy, believing the consumer succeeded.

## Consequences

This design assumes a single consumer instance per queue at
`prefetch(1)`. If a second consumer instance were started against the same
queue, RabbitMQ would round-robin deliveries between them, and any ordering
guarantee within `received.jsonl` (messages appearing in the order they
were published) would no longer hold — the file's write order would instead
reflect whichever consumer processed each message first.

If the consumer falls behind and the queue backs up for an extended period,
durability keeps every message safe on disk inside RabbitMQ, but nothing in
this design limits queue depth or alerts anyone that a backlog is
forming — the queue will grow until RabbitMQ's disk fills, at which point
RabbitMQ blocks producers rather than losing messages, which would surface
to callers of `POST /publish` as broker timeouts rather than a clear
"backlog" error.

`appendFileSync` writes the entire message body into a single line of
`received.jsonl` with no size limit; a 100MB message body would be written
in full, is never split or truncated, and would make that file
correspondingly harder to process line-by-line efficiently later, though it
would not corrupt the JSONL format itself.

The cost accepted here is throughput: publisher confirms mean every
`POST /publish` call blocks on a full network round trip to the broker
before returning `202`, and manual ack with `prefetch(1)` means the
consumer processes messages one at a time rather than in parallel. Both are
deliberate trades of speed for the guarantee that a `202` or a written line
in `received.jsonl` actually means what it claims.
