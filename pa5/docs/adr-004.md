# ADR-004 — Header-carried correlation id, file-backed idempotency, per-queue replay

**Status:** accepted
**Date:** 2026-10-25

## Context

The correlation id has to follow one order through three services. The canonical schema has `additionalProperties: false`, so it cannot be a field on the order body. It travels in `properties.headers["correlationId"]`. This is not AMQP's own `properties.correlationId`. The scaffold and the tests both read the header, so I followed them.

My first full test run failed tests 5, 9 and 10. Every failure involved payment. The logs showed `Not implemented — replace this with your logic`, so `payment-service/src/server.ts` still held the scaffold when I built. All five containers still reported `Healthy`, because that only means the process is alive. After I fixed the file and rebuilt, all 11 tests passed.

In test 6 the same order reaches notification-service twice. The log shows `duplicate skipped` for the second one.

## Decision

Each consumer parses the body inside the `try` block. A `SyntaxError` is permanent: the consumer publishes the original bytes and headers to `orders.invalid.exchange`, acks, and returns. Anything else falls through to the provided retry block, unchanged. That block calls `nack` without requeue until `getRetryCount` reaches `MAX_RETRIES - 1`. Then it publishes to `orders.dlq.exchange` with an `originQueue` header and acks.

Notification-service also treats a missing `correlationId` header as permanent, through a `PermanentError`. Without the id nothing can be deduplicated.

Notification-service re-reads `/data/processed-ids.json` on every message, keyed on `correlationId`. On a hit it acks and logs `duplicate skipped`. Otherwise it appends one line to `notification.log`, saves the id, publishes the result, and acks.

`POST /dlq/replay` in order-service takes messages from `orders.dlq` one at a time with `channel.get`. It republishes the original bytes to `orders.return.exchange`. The routing key is `originQueue`, and the headers come from `withoutRetryHistory`. Then it acks. A message with no `originQueue` is requeued after the loop, so it is not lost.

## Alternatives considered

I rejected `nack(msg, false, true)` for retries. It requeues at once, skips the one-second delay, and never produces an `x-death` header. `getRetryCount` would stay at zero and the message would loop forever.

I rejected an in-memory `Set` for idempotency. Test 6 passes with it, because nothing restarts mid-test. After `docker compose restart notification-service` the set is empty, and a redelivered order writes a second log line. The file costs one read per message, which I accepted.

I rejected replaying through `orders.exchange`. It is a fanout, so inventory and notification would process the order again, not only payment.

## Consequences

The idempotency check is check, work, record. If the service crashes after appending the log line but before saving the id, the redelivered message writes a second line. Two notification replicas would race on the same file, which has no lock. The file has no retention window, so it grows without bound.

Payment and inventory classify only invalid JSON as permanent. A message with no `correlationId` header is processed there with an undefined id. The three consumers disagree on what is permanent.

Replay publishes on a plain channel with no publisher confirm. If the broker loses the publish after I ack, the message is gone. Replaying twice is harmless, because the second run finds an empty DLQ and returns `replayed: 0`. If the original cause is still present, a replayed message uses its three attempts again and returns to the DLQ.

Nothing alerts anyone when `orders.dlq` fills. If inventory is down for longer than three retry cycles, the order sits in the DLQ and no downstream system learns about it.
